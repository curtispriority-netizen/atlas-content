# Atlas background research

The workflow is staged in `.github/workflows/research.yml`. It can run its fixture tests without credentials. Its scheduled publication job stays off until `ATLAS_PUBLISH_ENABLED=true`.

## What Atlas already does

The checked-in feed, schema and authoring instructions confirm two Claude jobs. The weekly job writes an ISO-week edition and updates `index.json` and `shown.json`. The daily paper-card job reads the **Atlas papers** Drive folder. It uses uploaded PDFs or queue markers with Atlas IDs and bibliography, finds free full text when possible, and writes `papers/<id>.json` and the paper index. The second appraisal is a separate Claude pass. The instructions require design-specific bias assessment, GRADE, and PEDro and review checks for uploaded PDFs. Existing cards show the source level and disagreements. The local preflight can detect an existing edition or a fully checked upload, without making model calls.

The question instructions describe Android searching Europe PMC for up to six drafts and queuing a question marker. The Claude job then searches PubMed and Europe PMC with PICO and synonyms, looks for reviews and guidelines, writes `questions/<id>.json`, and synthesises an answer from checked cards. That is the documented process. The app source and the running Claude task definitions were inaccessible, so the actual desktop sync path, exact weekly topics and search strings, hosting of the Claude tasks, and their subscription or API usage remain unverified. The Android feed contract is documented in [the content repository](https://github.com/curtispriority-netizen/atlas-content).

A read-only listing confirmed that the Drive folder exists and held two PDFs at the time of the audit. One matched the Atlas upload filename convention. A live Europe PMC check returned discovery records and three open-access full texts. One separate article request returned a server error. The worker records individual retrieval errors and can continue with other candidates.

## What this migration covers

GitHub Actions runs the Python worker on Wednesdays at 7:23 am Hobart time. It uses the existing feed paths and Atlas IDs. The proposed search in `scripts/research_config.json` covers tendinopathy, sports rehabilitation, and selected spine and lower-limb topics. Review the query against your usual watchlist before enabling it. The 28-day window covers recent PubMed-indexed records returned by Europe PMC, with open-access records prioritised. The default is up to eight candidates per run, with space for three discovery candidates. An edition has up to three new verified studies. Empty runs produce no edition.

The worker lists the full Drive folder, reads regular queue markers and recognises named PDF uploads. It verifies identity from bibliographic records, excludes records flagged as retractions or expressions of concern, and deduplicates on DOI, PMID and existing Atlas ID. It reads open-access Europe PMC XML where available. Text that lacks methods or results, scans without a usable text layer, oversized articles, unresolved identities, abstract-only appraisals and material disagreements stay outside the feed. An uploaded PDF requires matching open-access metadata and a private review of that exact file before the worker sends its text to the model. The worker records its source level, source hash, both readings, checks, decisions and usage in the private state repository. It keeps the source in memory during the run and stores short supporting excerpts in the private journal. The public feed receives summaries and citations.

The lower-cost model appraises first. A stronger model receives the original source and the same rubric in a separate request, with no draft or conversation history. Code checks the source excerpts, numbers, risk-of-bias and GRADE decisions. The stronger model compares the two structured readings in a third request without a third copy of the article. The worker holds disagreements for review. Atlas's existing validator checks card style, schema and links before a single feed commit can go to GitHub. The checks reduce publication risk. The paid stage run still needs a source-by-source review by a clinician.

Keep the legacy question, linked queue, deletion and measure-of-the-week workflows available. This migration leaves question reading lists and answers with their existing writer. Published cards and answers are preserved. A different Atlas ID for an already published DOI or PMID is held so the app's item references can be reconciled. The worker uses read-only access to Drive and leaves PDFs and markers in place. Uploaded-PDF anchor review is manual. Automatic editions record that external ratings were not searched.

## Setup and cutover

1. Put these changes on `atlas-content` main with publication off. GitHub requires the workflow on the default branch for manual dispatch and schedules. Run **Atlas research → Run workflow → test**. Offline cases use fixture responses and the real content validator.
2. Create an initialised **private** GitHub repository with a `main` branch for state. In `atlas-content`, create the `atlas-research` Actions environment and restrict it to `main`. Set repository variable `ATLAS_STATE_REPO` to `owner/repository`. Store `ATLAS_STATE_TOKEN` as an environment secret. Use a fine-grained token for that private repository alone with Contents read/write. The workflow checks repository visibility before writing. Public feed publishing uses its own repository's built-in token. A branch rule that rejects the bot's normal push will stop publication safely.
3. Enable the Drive API for a dedicated Google Cloud service account. Share only **Atlas papers** with that account as **Viewer**. Use a folder containing research only. Set `ATLAS_DRIVE_FOLDER_ID` to the folder ID and store the account JSON as environment secret `ATLAS_DRIVE_READER_JSON`. Store a project-scoped model key as environment secret `OPENAI_API_KEY`. Keep keys out of the checkout. [Google Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [Drive sharing](https://developers.google.com/workspace/drive/api/guides/manage-sharing), [GitHub Actions secrets](https://docs.github.com/en/actions/security-for-github-actions/security-guides/using-secrets-in-github-actions).
4. Set budget variables if needed. `ATLAS_RUN_MICRO_USD` defaults to `3000000` (USD 3 per workflow attempt). `ATLAS_MONTH_MICRO_USD` defaults to `15000000` (USD 15 per UTC month, including paid staging). These are conservative worker limits. It reserves before a call, reconciles returned usage at uncached rates and retains the reserve when billing is uncertain. Keep the private journal and token intact. The heavy estimate requires raising the eight-candidate setting. Use `retry_holds` on a manual stage run to reconsider held sources explicitly.
5. Run **stage** with representative test papers. Review the private `research-state.json` preview, supporting excerpts and both readings against the originals. Check eligibility, identity, PICO, every material number and confidence interval, bias, certainty, interpretation, and handling of conflicting or insufficient evidence. Confirm a publication example in both Atlas clients using their existing test or preview path before cutting over. A stage run writes only to private state. An intentional hold can give it a failed status even when it saved other verified previews. If a test uses an uploaded PDF, follow the anchor instructions below.
6. Keep a verified backup of the feed, Drive folder and legacy task definitions before changing those tasks. Once the pilot passes, disable the overlapping weekly publisher and narrow the daily writer to its remaining responsibilities, preserving the question and manual-review paths. Then set repository variable `ATLAS_PUBLISH_ENABLED=true`. Disable it to stop publication. Watch for GitHub's 60-day inactivity rule for public-repository schedules. [Scheduled workflow rules](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), [Inactivity rule](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows).

Use GitHub Actions' failed-run notifications for intervention. New actionable holds, failed requests, budget limits and validation failures are signalled there. Repeated known holds and quiet runs stay quiet. Optionally enable Issues read/write for the private state token, enable issues in that repository and set `ATLAS_PUBLICATION_NOTICES=true` to get an assigned private issue when a new feed commit is published. [GitHub Actions notifications](https://docs.github.com/en/subscriptions-and-notifications/how-tos/managing-github-actions-notifications).

### Review for uploaded PDFs

Add `anchors.json` to the private state repository. Key entries by lower-case DOI or PMID. Each entry includes `pdf_sha256` for the exact upload, `reviewed_by`, `external_searched` with the actual PEDro and review searches (30 words or fewer), and an `external` array of verified ratings with `source`, `rating`, `note`, `url`, and `agrees`. By adding a review, confirm the upload is the public paper with no private annotations. Use an empty `external` array only if no rating was found after those searches. A conflicting rating stays in the review queue. A replaced PDF needs a new review.

The fixture tests cover full text, abstract-only, duplicate, insufficient information, disagreement, empty inputs, simulated HTTP 429 and restart, source identity, both cost limits, provenance, and schema and style checks. Live API quality and authenticated Drive and app sync require the staged pilot.
